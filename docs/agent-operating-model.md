# Jarvis Agent Operating Model

Jarvis 采用三个互相制约的项目 Agent，围绕智能命令行持续演进：

```text
项目负责人
    │ 需求、版本目标、验收标准
    ▼
开发 Agent
    │ 代码、测试、构建、交付报告
    ▼
质量监督 Agent
    │ 审查结论和质量门禁
    ├── FAIL → 返回开发 Agent 修复
    └── PASS → 负责人验收并进入发布
```

## 标准循环

1. 负责人读取当前 `dev`、近期提交、构建状态和用户反馈。
2. 负责人创建需求说明，包含范围、非目标、验收标准和风险。
3. 开发 Agent 从最新 `dev` 创建独立分支实现需求。
4. 开发 Agent 必须运行测试、完整构建并提交交付报告。
5. 质量监督 Agent 独立审查；发现 Blocker/High 问题时退回开发 Agent。
6. 负责人根据验收标准确认需求完成，并决定合并到 `dev`。
7. 发布前负责人创建版本候选，质量监督 Agent 复核发行物、版本号和兼容范围。
8. 发布完成后记录变更、已知限制和下一版本候选需求。

## 分支约定

- `dev`：集成分支，只接收通过质量门禁的变更。
- `feature/<short-name>`：新能力和非紧急需求。
- `fix/<short-name>`：缺陷和安全修复。
- `release/<version>`：版本候选和发行准备。

禁止直接在 `dev` 上开发。合并前必须保持工作树干净，并保留可追溯提交。

## 质量门禁

```text
./gradlew test
./gradlew build
git diff --check
```

涉及命令执行、LLM、记忆、配置或网络的变更，还必须增加对应的安全和失败场景测试。

## 当前路线建议

- M1：稳定智能命令行、能力注册和短期上下文记忆。
- M2：能力描述/工具调用协议，替代固定的 type 数字协议。
- M3：持久化记忆、摘要、玩家偏好和可清理策略。
- M4：更多 Minecraft 能力、权限策略、可观测性和发行自动化。
